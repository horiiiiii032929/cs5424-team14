A
Five original design angles implemented; follow-ups through a115 and completed full-run audits are recorded below (22 October update).

1. Data placement — keep a merchant’s data together
Distribute customer, product, inventory, order and item tables by merchant_id so T1/T3/T4 can do more work on one worker. Update keys and merchant filters/joins; check ID-only operations and whether busy merchants overload one worker.

2. Data lookup — add indexes for slow reads
Test an orders index on merchant + customer + newest date, plus order_items(order_id) and inventory(product_id) indexes, to target order history (T3) and product lookup (T4). Faster reads may cost extra work on writes.

3. Transaction execution — place an order in one call
Move T1’s repeated client SQL steps into one stored function, keeping stock checks and all-or-nothing rollback. Test fewer client/database round trips first; running the function on the data’s worker can be tried later with idea 1.

4. Repeated calculations — maintain a small sales summary
For global sales (T6), keep exact counts and revenue per merchant/time bucket, updated in the same transaction as order changes, and read raw orders for partial boundary buckets. This could reduce repeated scans, but adds write contention and is the most complex idea.

5. Resource usage — tune memory and worker connections
Vary work_mem and the Citus executor pool limit one at a time within the same hardware budget. Check whether fewer concurrent worker tasks or less temporary-disk work improves throughput at higher client counts.
Suggested start: 2, then 1. In expt_a0/job-918524, T3 averaged 2.68 seconds at one client, making it the first bottleneck to investigate.

Compare each change with expt_a0 using the same A workload mix, data, client counts and isolation level. Measure throughput, latency and failures, verify correctness, then test useful combinations.

Write-path experiments
Workload A is 70% writes by weight (T1 36%, T2 20%, T5 10%, T7 5%, T8 2%, T9 2%). In parallel with the placement work above, we tested whether the update path itself could be made cheaper: fewer round trips per update, HOT updates, less waiting for WAL flushes, and a fixed lock order for T7. Each experiment starts from expt_a102 (job 965657), i.e. the baseline plus a102's three lookup indexes and its post-run correctness check (sql/verify.sql), and adds exactly one change. Workload mix, scale 1, SERIALIZABLE isolation, 60-second warmups, 600-second measurements and full log sampling are unchanged.
All runs were pinned to xcnf nodes. A first a12 submission that landed on xcnc nodes (job 967193) was cancelled and resubmitted (967217), since different hardware would confound a disk-sensitive setting. All four completed jobs exited 0 and passed all six post-run correctness checks: no negative inventory, no duplicate order or order-item IDs, and every order total equal to the sum of its items.
To observe the update path directly, run.sh also snapshots n_tup_upd, n_tup_hot_upd and n_tup_newpage_upd from pg_stat_user_tables on every worker, for the shards of customers, products, inventory and orders, before and after each measured run, and writes the difference to hot_updates.csv. The snapshots run outside the 600-second window. In a10 this returned no rows, because Citus hides shard tables from catalog queries on workers; from a14 onwards the query first sets citus.show_shards_for_app_name_prefixes = '*'.
On this base, overall TPS is 3.0–3.8 for every variant. T3 and T4 still account for about 94% of recorded time and the four single-row updates about 0.2%, so no write-path change can move overall TPS by more than run-to-run noise. That noise is visible in transactions none of these experiments touch: in the a10 run, T3, T4 and T6 were 9%, 14% and 9% slower at one client than in a102 (T3 2,911.7 vs 2,668.5 ms), and T4 was 53% slower at 16 clients. We therefore judge each change on the transactions it targets, and treat overall TPS differences within about 15% as noise.
expt_a10
T2, T5, T8 and T9 make up 34% of workload A. In the baseline each is already a single UPDATE (T2's stock check is already part of its WHERE clause), but each is wrapped in BEGIN/COMMIT. That costs three client-to-coordinator round trips instead of one, and adds a separate COMMIT at which Citus can turn a worker's serialization cancellation into the non-retryable shard-commit error shown in Figure 5.4.1.
Key Changes
Remove BEGIN and COMMIT from T2, T5, T8 and T9, so each UPDATE runs as one autocommit statement (Figure 3.10.1).
The UPDATE text, its inputs and the SERIALIZABLE isolation level are unchanged.
 
UPDATE inventory
SET quantity = quantity + (:inventory_change)::integer,
    updated_at = CURRENT_TIMESTAMP
WHERE inventory_id = (:product_id)::bigint
  AND merchant_id = (:merchant_id)::bigint
  AND product_id = (:product_id)::bigint
  AND quantity + (:inventory_change)::integer >= 0;

expt_a11
When PostgreSQL updates a row it writes a new row version. If the page has free space and no indexed column changes, this is a HOT (heap-only tuple) update: the new version stays on the same page and no index entries are added. Otherwise the new version goes to another page and every index on the table gets a new entry. Tables are loaded with full pages (fillfactor 100), so most inventory updates in a14 moved to a new page. Leaving 20% free space on each page should make them HOT.
Key Changes
Create customers, products, inventory and orders WITH (fillfactor = 80). a11's schema log confirms fillfactor=80 on the shards of all four tables.
Keep a14's VACUUM and CHECKPOINT after every load, so a11 differs from a14 only in fillfactor.
No index covers an updated column (quantity, order_status, email, price), so every update stays HOT-eligible.

The durability cost is real. With synchronous_commit = off, a commit is acknowledged before its WAL reaches disk, so a crash of any node can lose roughly the last 0.6 seconds (three times wal_writer_delay) of transactions that clients were told had committed. The database stays consistent, but those orders and stock changes disappear. Because T1 and T7 commit across shards with two-phase commit, a worker crash could also lose that worker's part of a transaction the coordinator reported as committed. expt_a13 (not run)
a13 planned to rewrite T7 so that it locks its two inventory rows in a fixed order, to prevent deadlocks. The evidence removed its premise. The preserved baseline (918524) recorded zero deadlock failures; all 126 failed transactions at 16/32/64 clients were T7 serialization failures ("could not serialize access due to read/write dependencies"). T7 looked up its rows by product_id while inventory was distributed by inventory_id, so each lookup scanned every inventory shard, and under SERIALIZABLE those scans conflicted with concurrent T1/T2 writes. a102's inventory(product_id) index removed those scans: T7's failures fell to zero and its one-client latency fell from 51.1 to 13.7 ms. a112 goes further by distributing inventory by product_id (similar to expt_b1), so a lock-order rewrite had nothing left to fix.

Write-path summary
On the a102 base, write-path tuning cannot move overall throughput while distributed reads take about 94% of recorded time. a10's autocommit is the one change with a clear, consistent benefit for its own transactions (29–74% lower median latency at every eligible client count) and is kept. a11 shows the HOT mechanism working (100% HOT updates) but needs a higher update rate to matter. a12 trades durability for no measurable gain, and a14 has no effect. Two lessons carry into the rest of this section: identical code varied by 9–14% in mean latency between single runs at one client, and more under contention, so smaller differences need repeats on matched nodes; and the client aborts that limit our fastest designs come mainly from T1's commit, not from the single-statement updates.

5. Task 4: Optimized design for Workload B
As suggested in the project description, the sequence of optimizations was progressively conducted. In general, each optimization was selected based on the measurements of the previous experiment, we selected the optimizations based on the workload weights and the performance bottlenecks observed in previous experiments.. Within the allowed tuning scope we changed the data distribution, the schema, the indexes and the transaction code.
expt_b1
T7 makes up 30% of workload B, and based on the vanilla baseline schema, each of its four SELECT queries will scan all 32 shards of inventory because they filter on product_id. In addition, T4 requires a repartition join between products and inventory on product_id. Distributing inventory on product_id, in the same co-location group as products, optimises both. The expected outcome is every T7 SELECT routes to one shard, and the T4 join becomes local to one shard.
Key Changes
Change the definition of inventory  so the primary key becomes (product_id, inventory_id);
inventory to be distributed on product_id and colocate_with => 'products'. 
T7’s two updates retain the selected inventory IDs and add their selected product IDs as routing predicates. The supplied fixture happens to use inventory_id equal to product_id, but the SQL looks up actual inventory IDs and does not rely on that equality.

expt_b3
T6 aggregates, per merchant, the total number of orders and revenue amount in the last 30 days (via created_at column), and returns the top 20. Under the vanilla baseline definition, there is no index on created_at, hence Postgres needs to perform sequential table scan.

Postgres stores a table in 8KB pages, each holding the data tuples. When it needs a row, it reads the entire page, so the cost of a query is mostly the number of pages it reads. From run.sh, orders timestamp are generated in the following fashion:

created_at = current_timestamp - (id * 31) mod 365 days
and every page contains rows throughout the year. An ordinary B-Tree index can quickly list all the rows in the last 30 days, but it stores only the indexed column, and not the other information that T6 requires. To get those, Postgres still has to read the rows, which means reading all the pages of the table. 
Key Changes
Create a covering index, orders(created_at) INCLUDE (merchant_id, total_amount) that is sorted by date, and each entry carries the other two columns T6 needs. Postgres will only need to perform an index-only scan to retrieve all the data required by T6.
Perform VACUUM to mark table pages all-visible in the visibility map, enabling index-only scans to skip the table.

6. Conclusion

Join-key colocation removed expensive distributed joins in Workload A: matched a112 delivered 16.8–28.2× fresh baseline throughput. a115’s complete audit verifies faster eligible observations, seven phase-complete cases (six with zero failures), all 12 passing validations, and repeated measurement/warmup aborts. For Workload B, the matched experiment showed that b6 achieved 20.86 times the baseline TPS at 1 client. However, aborted runs and serialization failures still limit comparisons at higher client counts. Final A/B choices remain with the team, with all abort/retry and correctness limitations retained.
Once joins improved, T6 became the main cost. Pre-aggregation is not automatically faster: a114’s maintained summaries slowed T6 in the A diagnostic, while a115’s timestamp index improved it. Isolated controls, repeated matched runs and explicit abort/retry reporting are essential; passing integrity checks do not make an aborted benchmark clean.
